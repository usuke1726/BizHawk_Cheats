
# ムシキングGC2

## ボイステキストバグ

アドレス `0x021D1046`

声の高さと速さは、料理ナビと同じく、上のアドレスに `0x8CE6` を引いた、`0x021C8360`


- ボイステキストデータ: `0x021D1046`
- 詳細データ: `0x021CAEA0` (-61A6)
- ボイス設定データ: `0x021C8360` (-8ce6)


構造は料理ナビと大体同じだが、特殊記法が使われている。

テキストの一部に

```
#V120\n#Z\n#S75\n

#B+500\n#A0\n#P0
(+: 0x2b, 0: 0x2d)
```

といった感じに`#<英字>`のprefixが付くことがある。

これはボイスの設定をしているみたい

- `#S`はスピード(値が大きいほど遅い)
- `#V`はボリューム(値が小さいほど声が小さい)
- `#P+<値>`はピッチ
- 主人公ボイス
    - `#B5250\n#S90\n#X103\n#I500\n#J20\n#S75`
- `#B5250` (主人公ボイスにて)
- `#X103` (主人公ボイスにて)
- `#I1000`: (冒頭のワルキングボイスにて) ?
- `#J70`: (冒頭のワルキングボイスにて)リバーブ?

## 所持カード

`0x21C3900`あたりから

- `21C3935`がムシno01のギラファ
    - `396A`でプラティオドン(no.54)が来た後、`396B`でムシキング(no.00)となり、その次は限定カード
    - `3971`が最後のアダーネプチューンで次の2byte(`72,73`)は未使用
- `21C3974`がわざno01のガンガンスマッシュ
    - `39A7`でばいがえし(no.52)が来た後、`39A8`でキングトルネードスロー(no.00)となり、その後はスーパー技が続く
    - 最後は`39BA`のスーパーアクシズスピン

## 主人公名

`0x021C3906` (SJIS)

あと `21C49B8`にもある

文字コードはsjis(他のテキストも同様)

```
"ひなみ": 82D0 82C8 82DD
"レイカ": 838C 8343 834A
"アキコ": 8341 834c 8352
```


### 主人公名のイントネーションについて

- レイカにすると、「レイカじゃないか」や「レイカさん」などのときに、レが一番低くてカに向けて高くなっていく、つまり想定とは逆のイントネーションになってしまう。
- これを根本的に解決する方法は見つかっていない。
- しかし、ROMないのボイスデータの`*n`部分を、`レ’ーカ`とし、その部分の他の`’`の箇所を削除、または`／`を名前の直後に配置することで、イントネーションを強引に解決することはできる。

一応以下のアドレスに設定した名前がカタカナになって反映されるが、直接いじっても効果が見られなかった

```

ほかにも以下の箇所があったが、いじっても反応ナシ
```

### テキストをいじる時はRAMをいじる！

イベントが始まったタイミングで、ROMの該当データを丸ごとRAMに読み込んで、そちらを使用するので、
GBAのときのように逐一いじるにはRAMの方をいじる必要がある。

単純に、ROMの方のバイト列で検索をかければアドレスはすぐに見つかる。そのアドレスを用いて `mushi.dump_text` してテキストと開始アドレスを吐かせればよい。

**アクション領域は大体 `0x021E7860` あたりから。**

その後にテキストが来るので、そこから探すとよい。

## 会話データの構造

基本的に、**処理部分領域 → テキスト/ボイステキスト領域 → ボイスアドレス領域**の順に並んでいる。

目印:

- 処理部分領域: `******E3`, `******E5`, `******EB` など、末尾に`E*`がある4byteデータが整列して並んでいる
- テキスト/ボイスアドレス領域: Shift JISっぽいデータ(例えば以下のような値)が(整列されずに)続いている
    - `82 **`(ひらがな), `83 **`(カタカナ)
    - `8140`(全角スペース), `0A`(改行文字)
- `******02`系の**RAMアドレス**っぽい4byte値が整列して並んでいる

### 処理部分領域

立ち絵表示などの処理(GBAではアクションと呼んでいたアレ)を担当

#### 立ち絵変更アクション

末尾`A0E3`(MOV命令)のデータが2byte目を`00`, `10`, `20`, `30`と連番にして4つ並んでいる。その直後に`******EB`命令(BL命令)が続いている。

例:

```
0x02F0B6C (RAMでは0x021E7BCC)から
3300A0E3 0110A0E3 0020A0E3 0030A0E3 0C45FAEB
```

- `33 00`で0番レジスタに`33`を格納
- `01 10`で1番レジスタに`01`を格納
- `00 20`で2番レジスタに`00`を格納
- `00 30`で3番レジスタに`00`を格納

この4つの値の意味はGBAと同じ: `<person> <expr> <fading> <chara>`

- `person`: 立ち絵としての人物番号
- `expr`: 表情番号
- `fading`: スライド(1), 一瞬(2), フェード(3)
- `chara`: 内部処理(吹き出し)としての人物番号

GC1から引継がれたキャラ(ひなみやネブ博士など)は、GBAと同じ`person`IDが使われ、\
GC2初出キャラは、`0x33`から主人公(男/女), 主人公, シン, ...と並んでいる。(最後は`5F`)

なお、BL命令のジャンプ先アドレスは次の通り:
- 左: `0x02079014`
- 右: `0x02078DB8`

#### 左右両方の立ち絵を変更するGC2初出アクション

左右両方同時に表情変更したりフェードインさせることができる。

立ち絵変更アクションのように見えて、`chara`が`00`でない場合はこっちを疑うとよい。

例:

```
0x02F0DC0 (RAMでは0x021E7E20)
1C1080E5 0E00A0E3 00008DE5 0000A0E3
         ↑右立ち絵expr ↑
                    8DE5はSTR命令
    (直前の0番レジスタに格納した値をメモリに退避させる)
04008DE5 0200A0E3 08008DE5 3300A0E3
         ↑両立ち絵fading  ↑左person
         (両方一斉にスライド/フェードする)
0110A0E3 0020A0E3 1D30A0E3 3943FAEB
↑左expr ↑不使用 ↑右person
```

BL命令のジャンプ先は `0x02078B38`

#### 発話者変更アクション

**MOV命令が1個**だけでしかも**2番**レジスタ、その直後にBL命令が来る場合、こちらの可能性が高い。

例:

```
0x02F0BE0 (RAMでは0x021E7C40)
3320A0E3 443C9FE5 003093E5 3047FAEB
↑発話者は 33 = 主人公男/女

0x02F0CA8 (RAMでは0x021E7D08)
1D20A0E3 7C3B9FE5 043093E5 FE46FAEB
↑発話者は 1D = アキラ
```

BL命令のジャンプ先は `0x02079914`

#### BGM変更アクション

**MOV命令1個 + 0番**レジスタ。実際に値を変えて検証するのが良い。

**前作から引き継がれたものはIDが使いまわされている。**

例えば`01`は引き続きシラシドのBGM。

本作からのものは`19`(テリーのテーマ?)から順番に割り当てられている。

例:

```
0x02F0B14 (RAMでは0x021E7B74)
2600A0E3 F23EFAEB
↑アキラチュートリアルのさかえや到着時のBGM
```

BL命令のジャンプ先は `0x02077748`

#### 背景変更アクション

**MOV命令1個 + 0番**レジスタ。実際に値を変えて検証するのが良い。

**前作から引き継がれたものもIDは再割り当てされている。**

例:

```
0x02F0B20 (RAMでは0x021E7B80)
0600A0E3 4546FAEB => 背景変更
↑06はさかえやの背景
```

BL命令のジャンプ先は `0x020794A0`

### テキスト領域

表示・読み上げ両方のデータが混在する。各データの区切りは`00`(複数個の場合もあるし1つだけのこともある)

この領域は処理部分が終わった直後(`00`をはさまずに)に開始されるので、実際にhex editorで目で探すのが良さそう。

```
ここには
```

## ARMアセンブリのメモ

### 立ち絵変更処理のアドレス計算

```
** 左立ち絵 BL命令

0x2F0B7C
EBFA450C => offset FA450C = -(1000000-FA450C)=-5BAF4
-5BAF4 * 4 + 4 = -16EBCC
  2F0B7c - 16EBCC = 181FB0

0x2F0D0C
EBFA44A8 => offset FA44A8 = -(1000000-FA44A8)=-5BB58
-5BB58 * 4 + 4 = -16ED5C
  2F0D0C - 16ED5C = 181FB0


** 右立ち絵 BL命令

0x2F0C44
EBFA4443 => offset FA4443 = -(1000000-FA4443)=-5BBBD
-5BBBD * 4 + 4 = -16EEF0
  2F0C44 - 16EEF0 = 181D54
```

## 立ち絵を変更する

`0x218686C`から6*4=24byte分を、その前の`0x218683C`からの24byte分の値でコピーすると、レイカ表情01がシンの邪悪そうな立ち絵に変わる。

```
0x218686Cからのデータ
3C061800 94160000
00000000 00080000
D01C1800 00020000

ここのデータは、GBAののときのデータ(以下みたいな)に似ている！
lib.warr(0x08894E04, lib.htob("A496E009140F000038DFBE09000800003C62E30960000000")) -- タクま対戦時表情を01にする
lib.warr(0x088950D4, lib.htob("D483E109C40D000038DFBE0900080000DC67E30960000000")) -- アキラ対戦時表情を09にする

恐らく、立ち絵のドットデータ、カラーパレットデータなどのアドレスとバイト長などを指定しているものと思われる。

つまり、
3C061800              94160000
ドットデータ          ドットデータの長さ
00000000              00080000
タイルデータ          タイルデータの長さ
D01C1800              00020000
カラーパレット        カラーパレットの長さ

という構造。(これはGBAと同じ?)
```

- `0x0218692C`がレイカの対戦時表情(表情09)
- `0x02186884`が対戦後勝利立ち絵(表情02)
- `0x021868CC`が対戦後敗北立ち絵(表情05)

どうやら、GC1のキャラはアドレスが少し離れている模様。

ひなみ: `0x0218A35C`から:
- 01: `0x0218A35C`
- 02: `0x0218A374`
- 04: `0x0218A3A4`
- 06: `0x0218A3D4`
- 08: `0x0218A404`
- 09: `0x0218A41C`
- 0C: `0x0218A464`
- 0F: `0x0218A4AC`
- 15: `0x0218A53C`
- 16: `0x0218A554`

変更用スクリプト

```lua
local function reika(expr)
    return 0x218686C + (expr-1)*0x18
end
local function hinami(expr)
    return 0x0218A35C + (expr-1)*0x18
end

local function change_battle_face(addr1, addr2)
    for j = 0, 5 do
        w32(addr1+4*j, r32(addr2+4*j))
    end
end

change_battle_face(reika(0x09), hinami(0x08))
change_battle_face(reika(0x02), hinami(0x01))
change_battle_face(reika(0x05), hinami(0x16))
```

## 会話ジャンプ方法

いくつか手順を踏んでメモリサーチする必要がある。

1. ジャンプ直前の `****001A` 命令を探す -> そのアドレスを `A` とする。
    - そいつ自身を0で埋め尽くしたら、飛ぶ前の会話が自動で流れる & その直後の12byteくらいを0で埋め尽くしたら、Aボタンでその飛ぶ前の会話を送ったタイミングでフリーズするような場所が、該当の場所。
1. ジャンプ先の `****001A` 命令を探す -> そのアドレスを `B` とする。
    - 上と同じような場所を探す。
1. アドレス `from = A+4, to = B+4` に対して、次の `jump(from, to)` を実行。

```lua
---B命令は https://github.com/akatsuki105/gba-docs-ja/blob/main/arm7tdmi/arm/branch.md を参考.
---@param from int
---@param to int
local function calc_B_asm(from, to)
    from = from & 0xfffffffc
    to = to & 0xfffffffc
    local d = (to - 8 - from) // 4
    if d < 0 then
        d = 0x1000000 + d
    end
    assert(within(d, 0, 0xffffff), string.format("d: %d", d))
    return 0xEA000000 | d
end

---@param from int
---@param to int
---@return int prev_value
local function jump(from, to)
    local prev = r32(from)
    w32(from, calc_B_asm(from, to))
    return prev
end

-- 例1:
jump(0x021E7C84, 0x021E7EF4) -- アキラチュートリアルイベントで、最初のレイカのセリフの直後に暗転してアキラの紹介文に入る (暗転背景指定は021E7F74)
-- 例2:
jump(0x021E7D4C, 0x021E7C84) -- アキラチュートリアルイベントで、アキラの最初のセリフの直後、もう一度アキラの最初のセリフに戻る(つまり、そこのセリフをずっと繰り返す)
```
